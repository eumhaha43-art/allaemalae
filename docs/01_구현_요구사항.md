# Figma 디자인 기반 AI 챗봇 지원 커뮤니티 웹앱 구현 요청

> 0장(프로젝트 입력 정보)의 실제 값은 [`00_프로젝트_입력정보.md`](./00_프로젝트_입력정보.md)에 있다.
> 이 문서는 요구사항 원문이며, 0장은 빈 템플릿 상태 그대로 보존한다.

너는 기존 Figma 디자인과 서비스 기획을 실제 동작하는 웹앱으로 구현하는 프론트엔드 개발자다.

React + TypeScript + Vite를 사용한다.
이 프로젝트는 디자인이 이미 완료된 상태이므로 새로운 디자인을 만드는 작업이 아니다.

기존 디자인과 사용자 흐름을 유지하면서 다음을 구현한다.

1. PC에서는 화면 가운데 기기 목업 안에서 작동하는 웹앱
2. 모바일에서는 기기 목업 없이 실제 화면에 최적화되는 웹앱
3. 퍼소나 A는 신규 가입 경로로 진입
4. 퍼소나 B·C는 각각의 특성에 맞는 기존 사용자 더미데이터로 진입
5. 커뮤니티 이용을 보조하는 AI 챗봇

## 1. 기존 디자인과 구현 범위

Figma를 시각적 구현의 기준으로 사용한다.

색상, 타이포그래피, 간격, 모서리, 그림자, 이미지 비율,
아이콘, 컴포넌트 상태, 화면별 정보 우선순위를 유지한다.

임의로 디자인 시스템을 바꾸거나 유행하는 스타일을 덧붙이지 않는다.
기존 화면을 일반적인 템플릿형 커뮤니티나 관리자 대시보드로 재해석하지 않는다.

화면 전체를 이미지로 붙이고 투명한 클릭 영역만 얹는 방식은 금지한다.
텍스트, 버튼, 입력창, 목록, 카드 등을 실제 React 컴포넌트로 구현한다.

기존 코드가 있다면 먼저 폴더 구조와 의존성, 라우팅, 스타일 방식을 확인한다.
프로젝트를 불필요하게 재생성하거나 다른 프레임워크로 전환하지 않는다.

PC용 앱과 모바일용 앱을 각각 복제하지 않는다.
페이지·라우팅·상태·기능은 공유하고, 외부 표현 방식만 다르게 구성한다.

구현 범위는 제공된 기획과 Figma를 따른다.
채팅, 결제, 관리자 기능 등 기획에 없는 기능을 임의로 추가하지 않는다.

## 2. PC 화면: 가운데 기기 목업 + 서비스 관련 배경

### 외부 쇼케이스 영역

PC에서는 브라우저 화면 중앙에 기기 목업을 배치한다.
주변에는 서비스와 관련된 배경 이미지 또는 브랜드 배경을 표시한다.

배경 이미지, 배경색, 오버레이 강도, 기기 크기는 설정에서 교체할 수 있게 한다.
배경이 미제공이면 기존 브랜드 색상의 단색 또는 절제된 그라데이션을 사용한다.
제공되지 않은 이미지를 실제 제공 에셋인 것처럼 사용하지 않는다.

서비스명, 짧은 설명, 퍼소나 선택 도구는 기기 바깥에 둘 수 있다.
이 보조 영역 때문에 기기가 브라우저의 가로 중앙에서 밀리지 않게 한다.

### 기기 목업

목업에는 다음의 시각적 요소를 포함한다.

- 기기 외곽 프레임과 베젤
- 화면의 둥근 모서리
- 상단 시스템 상태바
- 기준 기기에 맞는 노치 또는 다이내믹 아일랜드
- 하단 홈 인디케이터

시스템 상태바는 서비스 내부의 앱 헤더와 다른 요소다.
홈 인디케이터는 서비스의 하단 내비게이션과 다른 요소다.

Figma에 시스템 상태바와 홈 인디케이터가 이미 있다면
중복으로 추가하지 않도록 분리해서 처리한다.

목업 장식은 클릭, 터치, 키보드 탐색을 방해하지 않게 한다.

### 크기와 스크롤

기기 내부는 Figma 기준 화면 크기를 유지한다.
콘텐츠가 길어져도 기기 자체가 세로로 늘어나지 않게 한다.

PC 브라우저 높이가 낮으면 목업 전체를 비율에 맞춰 축소하는
'화면에 맞추기' 방식을 제공한다.
이때 앱 내부의 기준 레이아웃 크기를 임의로 바꾸지 않는다.

축소하지 않은 '원본 크기 보기'도 가능하게 하고,
이 경우에는 바깥 영역의 스크롤을 허용한다.

일반 화면에서는 앱의 콘텐츠 영역을 스크롤한다.
앱 헤더와 하단 내비게이션의 고정 여부는 Figma 설계를 따른다.

처음 보는 사람이 스크롤 가능 여부를 알 수 있도록
기기 바깥에 '기기 안에서 스크롤해 보세요' 같은 안내를 표시한다.
이미 스크롤한 뒤에는 안내를 줄이거나 숨긴다.

모달, 바텀시트, 토스트, 플로팅 버튼은 기본적으로
브라우저 전체가 아니라 기기 내부 화면을 기준으로 표시한다.
모달의 어두운 배경이 PC 배경 전체를 덮지 않게 한다.

## 3. 모바일 화면: 목업 제거 + 실제 기기에 맞춘 웹앱

기본 전환 기준은 화면 너비 1024px로 제안한다.
1024px 이상에서는 PC 쇼케이스,
미만에서는 목업 없는 앱 화면을 사용한다.
실제 디자인 검토 후 이 기준은 설정에서 조정할 수 있게 한다.

User-Agent 문자열에만 의존하지 않고 화면 크기를 기준으로 대응한다.

모바일에서는 다음 요소를 제거한다.

- PC용 외부 배경과 서비스 소개 영역
- 기기 외곽 프레임과 베젤
- 목업용 상태바와 다이내믹 아일랜드
- 목업용 홈 인디케이터
- PC용 스크롤 안내

서비스 자체의 헤더, 뒤로가기, 하단 내비게이션은 유지한다.

모바일에서는 앱을 402px × 874px로 고정하지 않는다.
너비는 실제 화면에 맞추고, 높이도 현재 표시 가능한 영역에 대응한다.
PC 목업을 통째로 축소한 화면을 모바일에 보여주는 방식은 금지한다.

다음 viewport 설정을 적용한다.

width=device-width, initial-scale=1, viewport-fit=cover

사용자의 확대를 막는 user-scalable=no 같은 설정은 사용하지 않는다.

화면 높이는 100dvh를 우선 검토하고 필요한 fallback을 둔다.
노치와 홈 인디케이터 주변은 env(safe-area-inset-*)를 활용한다.
기존 디자인 여백과 안전 영역이 중복 적용되지 않게 한다.

상단 헤더, 스크롤 콘텐츠, 하단 내비게이션의 영역을 명확히 나눈다.
불필요한 이중 스크롤과 가로 스크롤을 만들지 않는다.

키보드가 열렸을 때 다음을 확인한다.

- 가입 폼의 현재 입력창이 가려지지 않는다.
- 댓글 입력창과 전송 버튼을 사용할 수 있다.
- 챗봇 입력창과 최근 메시지를 확인할 수 있다.

100dvh와 안전 영역 설정만으로 키보드 대응이 완료됐다고 판단하지 않는다.
실제 브라우저 동작을 확인하고 필요한 경우 추가 보정한다.

화면 크기가 바뀌어도 현재 페이지, 입력 내용, 로그인 상태가 초기화되지 않게 한다.

## 4. 퍼소나별 시연 진입 구조

A·B·C는 별도의 앱이나 관리자 권한 등급이 아니다.
같은 서비스에서 서로 다른 사용자 여정을 체험하기 위한 시연 시나리오다.

### 시연용 진입 도구

실제 서비스 UI와 구분되는 퍼소나 선택 도구를 제공한다.

PC에서는 기기 바깥의 패널로 제공한다.
모바일에서는 별도의 데모 진입 화면 또는 접을 수 있는 도구로 제공한다.

서비스의 가입 화면 안에 A·B·C 선택 항목을 임의로 삽입하지 않는다.

선택 도구에는 다음 정보가 드러나게 한다.

- 퍼소나 이름
- 신규 사용자 / 기존 사용자 구분
- 주요 이용 목적
- 이 퍼소나로 체험하기
- 해당 퍼소나의 시연 데이터 초기화

### A: 신규 가입 시나리오

처음 A를 선택하면 가입 전 상태에서 시작한다.

진입 흐름은 기존 기획을 따른다.
예를 들면 다음과 같다.

첫 방문 → 온보딩 → 회원가입 → 초기 설정 → 홈

Figma에 없는 단계를 억지로 추가하지 않는다.
반대로 실제로 설계된 가입 단계를 임의로 건너뛰지 않는다.

입력 검증, 필수 항목 확인, 이전·다음 이동,
선택 상태 유지, 가입 완료 후 화면 이동이 동작해야 한다.

가입 과정에서 입력한 닉네임과 관심사는
가입 완료 후 프로필과 관련 화면에 반영한다.

A의 초기 개인 활동 기록은 신규 사용자에 맞게 비워둔다.
작성 글, 저장한 글, 알림, 챗봇 이용 기록이 이미 가득 차 있으면 안 된다.

다만 신규 사용자라고 커뮤니티 전체 게시물까지 비우지는 않는다.
공개 피드는 볼 수 있고, 개인 기록은 빈 상태로 구분한다.

A 시나리오를 초기화하면 다시 가입 전 상태로 돌아가야 한다.

### B: 기존 사용자 시나리오

처음 B를 선택하면 가입과 초기 설정을 마친
로그인된 데모 사용자 상태로 진입한다.

기획에서 정한 홈 또는 핵심 화면으로 이동한다.
가입과 온보딩을 다시 요구하지 않는다.

B의 관심사, 이용 목적, 활동 특성에 맞는
프로필·피드·개인 기록을 연결한다.

### C: 다른 기존 사용자 시나리오

C도 기존 데모 사용자 상태로 진입한다.

단, B의 이름과 프로필 사진만 바꾼 복제 데이터로 만들지 않는다.
C의 목적과 관심사, 활동 특성이 실제 화면에 드러나게 한다.

B와 C 사이에서 무엇이 달라지는지 설명할 수 있어야 한다.
동일한 관심사나 데이터가 기획에 명시돼 있다면
차이를 억지로 만들지 말고 실제 기획을 따른다.

### 진입과 상태 유지

퍼소나를 선택한 최초 진입에서는 해당 시작 경로로 이동한다.
그 뒤 화면을 이동하거나 새로고침할 때마다 시작 화면으로 보내지 않는다.

새로고침하면 선택한 퍼소나와 진행 상태를 복원한다.
처음부터 다시 체험하는 동작은 '시연 초기화'로 구분한다.

발표용으로 퍼소나별 직접 진입 URL도 제공할 수 있게 한다.
URL의 퍼소나 값은 시연 상태 선택에만 사용한다.

퍼소나 선택이나 URL 파라미터를 실제 인증·권한 부여 수단으로 사용하지 않는다.

## 5. 퍼소나별 더미데이터와 상태 관리

더미데이터는 컴포넌트 JSX에 흩어 넣지 않고 별도 파일로 관리한다.
공통 커뮤니티 데이터와 퍼소나별 개인 데이터를 구분한다.

기획에 존재하는 항목에 한해 다음을 구성한다.

- 프로필과 관심사
- 가입한 커뮤니티 또는 팔로우한 주제
- 홈 피드의 구성과 노출 순서
- 작성 글과 댓글
- 좋아요와 저장한 글
- 알림과 읽음 상태
- 챗봇 이용 기록 또는 추천 질문

기획에 없는 기능을 더미데이터를 위해 새로 만들지 않는다.

게시물·작성자·댓글·저장 기록 등의 ID 관계를 일관되게 유지한다.
프로필의 작성 글 수와 실제 목록처럼 서로 연결된 수치도 맞춘다.

서비스 주제에 맞는 자연스러운 한국어 데이터를 사용한다.
'게시글 1', '내용입니다', Lorem ipsum으로 주요 화면을 채우지 않는다.
실제 학생의 개인정보나 실제 계정 정보는 사용하지 않는다.

같은 퍼소나로 다시 시연했을 때 결과를 재현할 수 있도록
초기 데이터를 무작위로 계속 바꾸지 않는다.

시연 중 작성, 좋아요, 저장 등의 변경 사항은 상태에 반영한다.
새로고침 이후에도 필요한 상태를 유지한다.

퍼소나별 저장 공간은 분리한다.
예: 서비스명:demo:v1:A / B / C

공통 초기 데이터는 공유할 수 있지만,
시연 중 변경되는 데이터는 퍼소나별로 격리한다.

퍼소나를 전환할 때 이전 사용자의 입력 중인 폼,
개인 기록, 진행 중인 챗봇 응답이 다른 퍼소나에 섞이지 않게 한다.

초기화는 해당 서비스와 해당 퍼소나 데이터에만 적용한다.
localStorage 전체를 지우는 방식은 사용하지 않는다.

브라우저 저장소를 사용할 수 없거나 저장 데이터가 손상된 경우에도
앱이 흰 화면으로 멈추지 않도록 안전한 초기 상태로 복구한다.

## 6. 커뮤니티 인터랙션과 AI 챗봇

### 커뮤니티

Figma에 표현된 주요 버튼과 사용자 흐름이 실제로 연결되게 한다.

기획 범위 안에서 목록 → 상세 → 댓글,
좋아요, 저장, 검색, 탭 전환, 프로필 이동 등이 동작하게 한다.

버튼을 눌렀을 때 성공 알림만 띄우고 실제 상태는 변하지 않는
형식적인 구현은 하지 않는다.

로딩, 데이터 없음, 검색 결과 없음, 입력 오류,
처리 실패와 같은 상태도 필요한 화면에 구현한다.

### AI 챗봇

이 서비스의 중심은 커뮤니티다.
AI 챗봇은 사용자의 커뮤니티 이용을 보조한다.

기존 기획에 없는 전면 챗봇 서비스로 바꾸지 않는다.
챗봇의 위치, 진입 방법, 화면 구조는 Figma를 따른다.

현재 퍼소나의 관심사와 이용 목적을
추천 질문이나 응답 맥락에 반영할 수 있게 한다.
같은 질문이라도 맥락이 실제로 다를 때만 차이를 둔다.

메시지 입력·전송, 응답 대기, 오류 안내, 재시도가 동작해야 한다.

AI 호출 로직은 UI 컴포넌트와 분리한다.
실제 API와 mock 응답을 교체할 수 있는 구조로 만든다.

API가 제공되지 않았다면 mock 모드로 구현한다.
정해진 응답을 실제 생성형 AI 응답이라고 설명하지 않는다.
시연 도구와 결과 설명에서 mock 여부를 확인할 수 있게 한다.

실제 API가 제공됐다면 지정된 서버 또는 서버리스 엔드포인트를 사용한다.
AI 제공자의 비밀 API 키를 브라우저 코드에 넣지 않는다.
VITE_ 환경변수에 비밀키를 넣는 방식도 금지한다.

API 오류 발생 시 mock 응답으로 조용히 바꾸고
실제 AI가 응답한 것처럼 표시하지 않는다.

회원가입과 로그인도 실제 백엔드가 없다면 데모 동작임을 구분한다.
실제 비밀번호를 localStorage 등에 저장하지 않는다.

## 7. 라우팅·폴더 구조·컴포넌트·상태 관리 구현 규칙

기존에 제시한 Figma 디자인, PC 기기 목업, 모바일 대응,
퍼소나별 시연, AI 챗봇 요구사항에 더해 아래 개발 규칙을 적용한다.

학생들이 코드를 읽고 담당 기능을 수정할 수 있도록 구현한다.
한 파일에 모든 화면과 로직을 넣지 않는다.
반대로 작은 기능을 지나치게 많은 파일과 추상화로 분리하지 않는다.

아래 폴더명과 URL은 기본 제안이다.
실제 기획과 Figma에 없는 화면이나 기능을 임의로 추가하지 않는다.

### 7-1. 기술 구성과 기존 프로젝트 확인

기본 기술은 React + TypeScript + Vite다.

기존 프로젝트가 있다면 먼저 다음을 확인한다.

- package.json과 실제 설치된 패키지 버전
- 기존 라우터 구성
- 폴더 구조와 파일명 규칙
- CSS 작성 방식
- 상태 관리 방식
- API 연결 여부
- 실행·타입 검사·빌드 스크립트

기존에 작동하는 구조가 있다면 그 방식을 우선 유지한다.
라우터 추가를 이유로 프로젝트를 재생성하거나
Next.js, SSR, React Router Framework Mode로 전환하지 않는다.

라우터가 없다면 React Router의 Declarative Mode를 기본안으로 사용한다.

- BrowserRouter: 브라우저 URL과 앱 연결
- Routes / Route: 경로와 페이지 연결
- Outlet: 공통 레이아웃 안의 하위 페이지 표시
- Link / NavLink: 사용자가 누르는 페이지 이동 링크
- useNavigate: 가입 완료 등의 처리 이후 이동
- useParams: 게시글 ID 등의 경로 값 확인
- useSearchParams: 검색어·필터 등의 쿼리 값 관리

이미 createBrowserRouter + RouterProvider 방식으로 구성돼 있다면
이를 유지하고 동일한 요구사항을 그 구조에 맞게 적용한다.

BrowserRouter와 RouterProvider를 중복으로 감싸지 않는다.
설치된 버전과 맞지 않는 import나 다른 모드 전용 API를 섞지 않는다.

### 7-2. 폴더 구조와 파일별 책임

기존 구조가 없다면 다음 정도의 구조를 기준으로 시작한다.
필요한 파일만 생성하고 빈 폴더와 불필요한 파일을 미리 양산하지 않는다.

```
src/
├─ main.tsx
├─ App.tsx
│
├─ routes/
│  ├─ AppRoutes.tsx
│  ├─ paths.ts
│  └─ guards/
│     ├─ RequireAuth.tsx
│     └─ GuestOnly.tsx
│
├─ layouts/
│  ├─ ShowcaseLayout.tsx
│  ├─ AuthLayout.tsx
│  ├─ MainLayout.tsx
│  └─ DetailLayout.tsx
│
├─ pages/
│  ├─ demo/
│  ├─ onboarding/
│  ├─ auth/
│  ├─ home/
│  ├─ community/
│  ├─ chatbot/
│  ├─ mypage/
│  └─ error/
│
├─ components/
│  ├─ common/
│  ├─ device/
│  └─ community/
│
├─ hooks/
├─ state/
├─ services/
├─ data/
│  ├─ common/
│  └─ personas/
├─ types/
├─ utils/
├─ config/
├─ styles/
└─ assets/
```

각 영역의 책임은 다음과 같이 구분한다.

main.tsx
- React 앱의 시작점
- 전역 스타일 불러오기
- 선택한 방식에 맞는 Router를 한 번만 연결

App.tsx
- 앱 전체에 필요한 Provider와 라우트 연결
- 개별 화면의 상세 UI나 더미데이터를 몰아넣지 않음

routes/
- URL과 페이지의 연결
- 공통 경로와 동적 경로 생성 함수
- 로그인 여부 등에 따른 접근 제어

layouts/
- 여러 페이지가 공유하는 화면 틀
- 헤더, 하단 내비게이션, 콘텐츠 영역 배치
- 개별 게시글 데이터나 챗봇 요청을 직접 관리하지 않음

pages/
- URL에 대응하는 실제 화면
- 공통 컴포넌트와 기능 로직을 조합
- 한 페이지에서만 쓰는 작은 컴포넌트는 해당 페이지 폴더에 둘 수 있음

components/
- Button, Input, Modal 등의 공통 UI
- DeviceFrame, StatusBar 등의 목업 요소
- PostCard, CommentItem 등의 재사용되는 커뮤니티 UI

hooks/
- 여러 곳에서 사용하거나 페이지에서 분리할 필요가 있는 React 로직
- useDemo, useChatbot 등 필요한 단위로 구성

state/
- 선택한 퍼소나, 데모 세션, 여러 화면이 공유하는 변경 데이터
- 상태를 변경하는 함수와 Provider

services/
- 게시글 조회·변경, 챗봇 요청 등의 데이터 처리 경계
- 실제 API와 mock 구현을 교체하는 위치

data/
- 공통 커뮤니티 초기 데이터
- A·B·C별 개인 초기 데이터
- 화면에서 직접 수정하지 않는 원본 seed 데이터

types/
- User, Persona, Post, Comment, ChatMessage 등의 공통 타입

utils/
- 날짜 표시, 문자열 처리, 입력값 검증 등의 일반 함수
- React 상태가 필요 없는 처리는 불필요하게 Hook으로 만들지 않음

config/
- 서비스명, 기기 크기, 배경, 데모 모드 등의 설정

styles/
- 전역 초기화 스타일과 공통 디자인 토큰

assets/
- 프로젝트에서 사용하는 이미지, 아이콘, 폰트 등의 에셋

### 7-3. 먼저 화면과 URL의 대응표를 작성한다

Figma 화면을 확인한 뒤 구현 전에 다음 표를 작성한다.

- Figma 프레임명
- 실제 화면명
- URL
- 페이지 컴포넌트
- 사용하는 레이아웃
- 로그인 필요 여부
- 진입 경로와 다음 행동
- 사용하는 데이터

Figma 프레임 하나를 무조건 페이지 하나로 만들지 않는다.

독립적인 방문·공유·뒤로가기가 필요한 화면은 라우트로 구분한다.
같은 화면의 버튼 상태, 오류 표시, 단순 모달은 컴포넌트 상태로 처리한다.

다음은 URL 설계 예시이며, 실제 기획에 있는 항목만 채택한다.

| URL | 역할 | 페이지 예시 |
|---|---|---|
| / | 최초 진입 분기 | EntryRedirect |
| /demo | 시연용 퍼소나 선택 | DemoPage |
| /onboarding | 첫 방문 안내 | OnboardingPage |
| /login | 로그인 | LoginPage |
| /signup | 회원가입 | SignupPage |
| /signup/profile | 가입 후 초기 설정 | ProfileSetupPage |
| /home | 홈 | HomePage |
| /community | 커뮤니티 목록 | CommunityPage |
| /posts/:postId | 게시글 상세 | PostDetailPage |
| /posts/new | 게시글 작성 | PostCreatePage |
| /posts/:postId/edit | 게시글 수정 | PostEditPage |
| /chatbot | 챗봇 화면 | ChatbotPage |
| /mypage | 내 정보·활동 | MyPage |
| * | 존재하지 않는 경로 | NotFoundPage |

챗봇이 별도 화면이 아니라 바텀시트로 설계됐다면
/chatbot 페이지를 억지로 추가하지 않는다.

기획에 로그인 화면이 없거나 온보딩 단계가 다르면
예시를 그대로 강요하지 말고 실제 사용자 흐름을 따른다.

게시글마다 별도 페이지 파일을 만들지 않는다.
PostDetailPage에서 postId에 해당하는 데이터를 조회한다.

잘못된 경로와 존재하지 않는 게시글은 구분한다.

- 잘못된 URL: 페이지를 찾을 수 없음
- 없는 게시글 ID: 삭제됐거나 존재하지 않는 게시글
- 권한이 없는 게시글: 접근할 수 없음

모든 오류를 무조건 홈으로 보내서 숨기지 않는다.

### 7-4. 공통 레이아웃과 기기 목업을 라우터에 연결한다

기기 목업은 페이지마다 복사하지 않는다.
서비스 화면 전체를 감싸는 공통 레이아웃에서 한 번만 구성한다.

개념적인 구조는 다음과 같다.

```
Router
└─ 앱 상태 Provider
   └─ AppRoutes
      ├─ 시연용 진입 화면
      └─ ShowcaseLayout
         └─ DeviceFrame
            └─ AppViewport
               └─ Outlet
                  ├─ AuthLayout → 가입·로그인 관련 화면
                  ├─ MainLayout → 주요 메뉴 화면
                  └─ DetailLayout → 상세·작성 등의 화면
```

실제 라우트 설정에서는 레이아웃과 하위 페이지를 중첩 연결하고,
각 레이아웃의 Outlet 위치에 자식 화면을 표시한다.

ShowcaseLayout
- PC에서는 관련 배경과 중앙 기기 목업 표시
- 모바일에서는 외부 배경과 목업 장식 제거
- PC용 퍼소나 선택 패널 등 시연 도구 배치

AuthLayout
- 온보딩·가입·로그인 계열의 화면 틀
- 일반 하단 내비게이션은 기본적으로 표시하지 않음
- 실제 표시 여부와 헤더는 Figma를 따름

MainLayout
- 홈·커뮤니티·마이페이지 등 주요 메뉴의 공통 틀
- 앱 헤더와 하단 내비게이션
- 내부 페이지가 들어가는 Outlet

DetailLayout
- 상세·작성·수정·독립형 챗봇 등의 화면 틀
- 뒤로가기, 제목, 완료 버튼 등의 구성
- 하단 내비게이션 표시 여부는 실제 디자인을 따름

레이아웃의 모양과 로그인 접근 권한은 별개로 관리한다.
AuthLayout을 사용한다고 모두 비로그인 전용 페이지인 것은 아니다.

PC·모바일 전환 때문에 앱의 주요 컴포넌트를 교체하거나
라우터와 Provider를 다시 생성하지 않는다.

가능하면 동일한 컴포넌트 트리에서 CSS로 표현을 바꾼다.
PC용 HomePage와 모바일용 HomePage를 따로 만들지 않는다.

AppViewport는 앱의 화면 경계를 담당한다.
각 레이아웃 안에서 헤더·스크롤 콘텐츠·하단 영역을 배치한다.

모달·바텀시트용 portal 대상은
기기 내부이면서 스크롤 콘텐츠 바깥에 마련한다.
PC에서 모달이 브라우저 전체를 덮지 않게 한다.

### 7-5. 퍼소나와 로그인 상태를 분리한다

퍼소나 선택과 로그인 여부를 같은 값으로 취급하지 않는다.

구분해야 할 상태는 다음과 같다.

- personaId: A / B / C 중 어떤 시나리오인지
- sessionStatus: 초기 복원 중 / 비로그인 / 로그인
- currentUser: 현재 사용자 정보 또는 null
- profileCompleted: 초기 설정 완료 여부

A는 처음에는 비로그인이지만 가입 후에는 로그인 사용자가 된다.
B·C도 로그아웃할 수 있으므로
"B이면 항상 로그인" 같은 조건을 매번 적용하지 않는다.

퍼소나는 초기 시나리오와 데이터 선택 기준이다.
실제 인증이나 관리자 권한의 대체 수단이 아니다.

페이지 접근 규칙은 다음과 같이 구분한다.

1. 공개 페이지
   - 비로그인 사용자도 접근 가능
   - 공개 홈·게시글 열람 여부는 서비스 기획을 따름

2. 로그인 필요 페이지
   - RequireAuth 등으로 접근 조건을 공통 처리
   - 비로그인이면 로그인 또는 기획된 가입 경로로 안내

3. 비로그인 전용 페이지
   - 이미 로그인한 사용자는 로그인·가입 화면으로 다시 보내지 않음
   - 초기 설정 완료 여부에 따라 적절한 화면으로 이동

4. 초기 설정 페이지
   - 가입은 했지만 초기 설정을 마치지 않은 사용자가 접근
   - 단순 비로그인 전용 가드 아래에 넣지 않음

저장된 상태를 복원하는 중에는 접근 여부를 성급하게 판단하지 않는다.
복원이 끝나기 전에 로그인 화면이 잠깐 나타나거나,
기존 데이터를 빈 초기값으로 덮어쓰지 않게 한다.

보호된 페이지에 접근하다가 로그인했다면
허용된 원래 목적지로 돌아갈 수 있게 한다.

복귀 경로는 검증된 앱 내부 경로만 허용한다.
외부 URL이나 로그인 화면으로 반복 이동하는 경로는 거부한다.

비로그인 사용자가 댓글·좋아요 등 제한된 동작을 누르는 경우도
페이지 접근과 별도로 처리한다.

실제 API를 연결할 경우 데이터 조회·변경 권한은 서버에서도 검증한다.
프론트엔드에서 버튼과 페이지를 숨긴 것만으로 보안을 구현했다고 하지 않는다.

### 7-6. 퍼소나별 최초 진입과 직접 URL 접근

데모 모드의 기본 진입 규칙은 다음과 같다.

퍼소나 선택 기록 없음
→ /demo

A 최초 시작 또는 A 초기화
→ 기존 기획의 첫 방문·가입 시작 화면

A 가입 및 초기 설정 완료
→ /home 또는 기존 기획의 완료 후 화면

B·C 최초 시작
→ 각 퍼소나의 기존 사용자 데이터 준비
→ /home 또는 기획에서 지정한 핵심 화면

퍼소나별 직접 진입 주소를 제공한다.

예:
- /demo?persona=A
- /demo?persona=B
- /demo?persona=C

직접 진입 파라미터는 해당 시나리오를 선택하는 데 사용한다.
기존 진행 데이터가 있으면 이어서 체험한다.
데이터 초기화는 명시적인 초기화 동작으로만 수행한다.

파라미터 처리 후에는 실제 시작 화면으로 replace 이동해
같은 초기화·선택 처리가 뒤로가기 때 반복되지 않게 한다.

퍼소나 선택 때문에 다음처럼 서비스 URL 전체를 복제하지 않는다.

금지 예:
- /a/home
- /b/home
- /c/home
- /desktop/home
- /mobile/home

A·B·C와 PC·모바일은 같은 서비스 URL을 사용한다.
보여주는 데이터와 외부 표현 방식만 달라진다.

최초 진입 분기는 /와 명시적인 데모 진입에서 처리한다.
사용자가 /posts/p001을 직접 열었는데
전역 효과가 실행돼 무조건 /home으로 보내면 안 된다.

직접 연 URL은 필요한 상태 복원과 접근 확인 후 유지한다.
퍼소나 선택이 먼저 필요하다면 원래 목적지를 안전하게 보존한다.

데모 모드를 사용하지 않는 실제 서비스에서는
퍼소나 선택 없이 정상적인 사용자 진입 흐름을 제공한다.

### 7-7. 이동·뒤로가기·검색·스크롤 규칙

앱 내부의 일반 페이지 이동에는 Link를 사용한다.
하단 내비게이션처럼 활성 상태가 필요한 링크는 NavLink를 사용한다.

가입 완료, 글 저장 완료 등의 처리 이후 이동은 useNavigate를 사용한다.
앱 내부 이동에 window.location.href를 반복 사용하지 않는다.

하단 메뉴의 활성 상태는 현재 URL에서 판단한다.
별도의 selectedMenu 상태와 URL이 서로 어긋나지 않게 한다.

검색어·필터처럼 새로고침하거나 공유해도 유지돼야 하는 조건은
필요한 범위에서 URL 쿼리로 관리한다.

예:
- /community?category=review&sort=latest
- /community?q=검색어

입력 중인 검색어와 검색을 확정한 결과 조건은 구분할 수 있다.
키를 입력할 때마다 불필요한 방문 기록을 쌓지 않는다.

단순 모달 열림 여부는 기본적으로 화면 상태로 관리한다.
공유 주소나 브라우저 뒤로가기가 필요한 모달만 라우트와 연결한다.

뒤로가기 버튼은 앱 내부에서 이동해 온 기록이 있을 때 돌아간다.
외부에서 상세 URL로 바로 들어온 경우에는
커뮤니티 목록 등 정해진 fallback 경로로 이동한다.

history.length만 보고 안전한 앱 내부 이전 화면이 있다고 가정하지 않는다.

스크롤은 실제 앱 콘텐츠 컨테이너를 기준으로 관리한다.

- 새로운 상세 화면 진입: 기본적으로 상단에서 시작
- 목록 → 상세 → 뒤로가기: 목록의 검색 조건과 스크롤 위치 복원
- 주요 탭 재방문: 기획에서 정한 스크롤 정책 적용
- 챗봇: 일반 페이지와 구분되는 대화 스크롤 정책 적용

기기 내부가 스크롤되는데 window.scrollTo만 호출하는 구현은 하지 않는다.
현재 사용하는 라우터 모드와 스크롤 컨테이너에 맞게 구현한다.

### 7-8. 상태와 더미데이터의 저장 위치

상태를 다음 기준으로 나눈다.

화면 내부 상태
- 모달 열림, 입력 중인 값, 펼침 여부 등
- 해당 페이지 또는 가장 가까운 공통 부모에서 관리

URL 상태
- 현재 페이지, 게시글 ID, 검색어, 필터 등
- 라우터에서 읽고 변경
- 같은 값을 별도의 전역 상태에 중복 저장하지 않음

앱 공유 상태
- 선택한 퍼소나, 현재 사용자
- 여러 화면에서 함께 사용하는 게시글·저장·좋아요 변경 사항
- 필요한 Provider에서 관리

지속 저장할 데모 상태
- 퍼소나별 진행 상황과 활동 기록
- 저장·복원 로직을 한곳에 모아 관리

처음에는 useState와 필요한 Context를 기본으로 검토한다.
상태 변경 규칙이 복잡해지면 useReducer를 검토한다.
명확한 이유 없이 Redux·Zustand 등의 도구를 추가하지 않는다.
이미 사용 중인 상태 관리 도구가 있다면 기존 방식을 따른다.

컴포넌트마다 localStorage를 직접 읽고 쓰지 않는다.
변경은 상태 관리 함수를 통해 수행하고 저장 로직은 분리한다.

원본 seed 데이터와 사용자가 변경하는 상태를 분리한다.
seed 객체를 직접 수정하지 않는다.

좋아요, 저장, 글 작성 등의 변경은 관련 화면에 일관되게 반영한다.

예:
- 목록에서 좋아요 → 상세에서도 같은 상태
- 상세에서 저장 → 마이페이지 저장 목록에도 반영
- 작성 글 삭제 → 목록·상세·내 활동 기록에서 일관되게 처리

퍼소나별 데이터 저장 공간과 요청 결과를 분리한다.
전환 전 사용자의 늦게 도착한 챗봇 응답이나 API 결과가
전환 후 사용자의 화면에 반영되지 않도록 취소하거나 무시한다.

페이지가 바뀔 때마다 전체 Provider를 초기화하지 않는다.
다만 퍼소나가 바뀔 때는 이전 사용자의 임시 입력이 남지 않도록
필요한 화면 상태만 의도적으로 정리한다.

### 7-9. 컴포넌트·타입·스타일 작성 기준

페이지 컴포넌트는 화면 구성을 담당한다.
복잡한 데이터 처리, 저장소 처리, API 호출을 한 파일에 몰아넣지 않는다.

재사용 컴포넌트는 props로 필요한 데이터를 받는다.
PostCard 내부에서 특정 퍼소나의 seed 파일을 직접 import하지 않는다.

서비스 처리는 services, 공유 상태 변경은 state,
재사용되는 React 로직은 hooks에 둔다.

실제 API와 mock 구현은 가능한 한 같은 입출력 타입을 사용한다.
연결 방식이 바뀌었다고 페이지 전체를 다시 작성하지 않게 한다.

TypeScript에서는 다음을 지킨다.

- 컴포넌트 props와 주요 데이터 타입 명시
- any나 @ts-ignore로 오류를 일괄 숨기지 않음
- URL 파라미터가 없거나 잘못된 경우 처리
- 저장소에서 읽은 데이터의 누락·손상 여부 확인
- 타입 단언만으로 외부 데이터가 검증됐다고 간주하지 않음

컴포넌트 파일명은 HomePage.tsx, PostCard.tsx처럼 의미를 드러낸다.
HomeA.tsx, HomeB.tsx, HomeC.tsx처럼 퍼소나별 화면을 복제하지 않는다.

스타일은 기존 프로젝트 방식을 유지한다.
미정이라면 CSS Modules와 공통 디자인 토큰을 기본안으로 사용한다.

전역 CSS에는 초기화·폰트·디자인 토큰 등 공통 규칙을 두고,
페이지·컴포넌트의 스타일은 해당 영역에 가깝게 둔다.

학생이 수정할 수 있도록 필요한 주석을 작성한다.
문법을 그대로 반복하는 주석보다
상태 분리 이유, 라우트 접근 조건, PC·모바일 차이를 설명한다.

### 7-10. 구현 순서와 확인할 결과

다음 순서로 구현한다.

1. 기존 코드와 Figma 확인
   - 화면·URL·레이아웃 대응표 작성
   - 실제 사용 중인 패키지와 라우터 방식 확인

2. 공통 구조 연결
   - Router와 Provider 연결
   - PC 목업·모바일 공통 화면 틀 구현
   - 주요 경로와 NotFound 화면 연결

3. 대표 사용자 흐름 완성
   - A의 가입 시작부터 홈 진입까지
   - B·C의 기존 사용자 진입과 데이터 차이 확인
   - 목록 → 상세 → 뒤로가기 연결

4. 기능 연결
   - 커뮤니티 상태 변경
   - 챗봇과 API/mock 연결
   - 오류·빈 상태·로딩 처리

5. 검증과 인계
   - 타입 검사·빌드
   - 배포된 URL 직접 접근과 새로고침
   - 학생이 수정할 파일 위치 정리

기존 프로젝트에서 실행 가능한 검사 스크립트를 확인하고 사용한다.
Vite 개발 서버에서 화면이 보인다는 이유만으로
타입 검사와 프로덕션 빌드까지 통과했다고 판단하지 않는다.

BrowserRouter를 사용하는 SPA는 배포 환경에서도
하위 URL이 앱 진입 파일로 연결되도록 설정한다.

Vercel이라면 현재 프로젝트 구성에 맞는 SPA fallback을 확인한다.
API 경로와 정적 파일 요청까지 앱 HTML로 잘못 보내지 않도록 검증한다.
배포를 피하려고 임의로 HashRouter로 바꾸지 않는다.

라우팅과 상태에 대해 다음을 추가로 확인한다.

- [ ] 주요 화면을 각각 URL로 직접 열 수 있다.
- [ ] 상세 페이지에서 새로고침해도 정상 표시된다.
- [ ] 브라우저 뒤로가기·앞으로가기가 의도대로 작동한다.
- [ ] 외부에서 직접 연 화면의 뒤로가기 fallback이 있다.
- [ ] 없는 URL과 없는 게시글을 구분해 처리한다.
- [ ] 로그인 상태 복원 중 잘못된 리다이렉트가 발생하지 않는다.
- [ ] A는 가입 후 정상적인 로그인 사용자 흐름으로 이어진다.
- [ ] B·C가 로그아웃해도 자동으로 다시 로그인되지 않는다.
- [ ] 퍼소나 선택 때문에 서비스 페이지가 복제되지 않는다.
- [ ] PC·모바일 전환으로 현재 화면과 입력값이 초기화되지 않는다.
- [ ] 목록의 검색 조건과 필요한 스크롤 위치가 복원된다.
- [ ] 개인 상태와 비동기 응답이 퍼소나 사이에 섞이지 않는다.
- [ ] 시연 초기화와 단순 새로고침이 구분된다.
- [ ] 타입 검사와 빌드를 실제 실행한 결과가 기록된다.

마지막으로 다음 내용을 남긴다.

- 최종 폴더 구조와 역할
- Figma 화면·URL·컴포넌트 대응표

## 8. 검증 및 결과 보고

최소한 다음 화면 조건에서 확인한다.

- PC: 1440×900, 1366×768
- 모바일: 너비 360, 390, 402, 430
- 모바일 가로 방향
- 모바일 키보드가 열린 가입·댓글·챗봇 화면

다음 항목을 검증한다.

- [ ] PC에서 기기가 화면 중앙에 놓인다.
- [ ] 낮은 PC 화면에서도 목업의 아래쪽이 접근 불가능하게 잘리지 않는다.
- [ ] PC 배경과 기기 설정을 쉽게 교체할 수 있다.
- [ ] 모바일에서 기기 테두리와 가짜 시스템 UI가 사라진다.
- [ ] 모바일에서 실제 화면 너비에 맞고 가로 스크롤이 발생하지 않는다.
- [ ] 모달·바텀시트·토스트가 의도한 앱 영역 안에서 표시된다.
- [ ] A는 가입 전부터 시작하며 가입 결과가 홈과 프로필에 반영된다.
- [ ] A의 개인 빈 상태와 공개 커뮤니티 데이터가 구분된다.
- [ ] B·C는 기존 사용자 상태로 진입한다.
- [ ] B·C의 데이터가 각 퍼소나의 실제 기획과 연결된다.
- [ ] 퍼소나를 전환해도 다른 사용자의 개인 상태가 섞이지 않는다.
- [ ] 새로고침과 화면 크기 변경으로 진행 상태가 의도치 않게 초기화되지 않는다.
- [ ] 퍼소나별 초기화 후 동일한 시나리오를 다시 체험할 수 있다.
- [ ] 브라우저 뒤로가기와 배포 환경의 직접 URL 진입이 동작한다.
- [ ] mock 기능과 실제 API 기능이 명확히 구분된다.
- [ ] 프로젝트의 타입 검사와 빌드가 통과한다.

사용 가능한 검사 스크립트를 확인한 뒤 실제로 실행한다.
실행하지 못한 검사나 실기기 테스트를 통과했다고 말하지 않는다.

작업 결과는 다음 내용으로 정리한다.

- 구현한 화면과 연결된 사용자 흐름
- PC·모바일의 표시 방식
- A·B·C별 시작 경로와 데이터 차이
- 배경·기기·퍼소나 데이터를 수정하는 위치
- 실제 구현 / mock 구현 / 미구현 구분
- 실행한 검증과 결과
- 확인하지 못한 자료와 남은 문제
